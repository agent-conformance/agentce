# 0013 — Server-side leakage guard without disclosing the guarded lists

Status: accepted
Spec refs: —

## Context

Two families of protection ran only on the maintainer's own machine, as local git hooks wired through
`core.hooksPath`:

- the **leakage guards** — refuse to commit a private path, refuse added file content that carries a
  private term, and refuse a commit message that carries a private term or a message-denylisted term; and
- the **spec validators** — `spec/vocab/check_vocab.py` (the evidence vocabulary) and
  `spec/validate_examples.py` (the worked examples against their schemas).

Nothing enforced either family server-side. A contributor who never installed the hooks, or the
maintainer on a fresh clone, could push content or a message that should have been refused, and CI said
nothing; the published vocabulary and schema examples could drift on a merge with no gate to catch it.
The one hygiene job checked only that specification *paths* were untracked — never added *content*, never
the message rule, never the validators.

Moving the validators into CI is routine. The leakage guard is not, because of a constraint particular to
it: the two guarded lists are themselves private, and each contains the very strings it bans, so neither
list may enter this public repository. The obvious "run the same match in CI" would require shipping the
lists — a non-starter. The guard has to enforce the lists server-side while never disclosing them, and it
has to be safe on pull requests from forks, where no repository secret is available and the checked-out
code is untrusted.

## Decision

1. A `spec-validators` CI job (`.github/workflows/guards.yml`) runs both validators on every push and
   pull request via `uv`, so a broken vocabulary or an example that no longer satisfies its schema fails
   the build.

2. A `leak-guard` CI job runs `tools/leak_guard.py` on every push and pull request. The guard matches the
   added content of the diff and the commit messages in range against **salted SHA-256 digests** of the
   normalized terms, committed as `tools/leak_tokens.hashes` (one `scope digest` line each; no cleartext).
   Normalization is shared by the generator and the guard: lowercase, maximal `[a-z0-9]+` runs joined by
   single spaces; the guard hashes every n-gram up to the recorded `ngram_max` and flags any digest match.
   On a hit it prints only a **stable message key and a `file:line` (or `commit:<sha>`) location — never
   the matched text**. `scope both` terms (the private terms) are banned in content and in messages;
   `scope message` terms (the message-denylist) are banned in messages only.

3. The salt is committed alongside the digests, so the guard needs **no secret and no private checkout**
   and is safe under the default `pull_request` trigger; `pull_request_target` is never used and the job
   holds only `contents: read`. This is what lets the floor cover fork pull requests — the exact bypass
   this change closes.

4. Registering the two jobs as **required** status checks on `main` is a branch-protection change that no
   commit can make; it is tracked as a human action for the maintainer.

The digests are regenerated by the maintainer from the private lists whenever those lists change; the
lists and the generator stay in the private tree and never enter this repository.

## Alternatives considered (with why not)

- **Ship the lists to CI and grep (full fidelity).** Rejected outright: it publishes the private lists,
  which contain the very terms they ban. The whole problem is that these lists cannot be public.
- **Keyed HMAC on trusted refs only (a secret salt, non-fork events).** Stronger against offline attack,
  but as the *sole* mechanism it leaves fork pull requests with no server-side guard — the bypass #35 is
  about. Kept as an optional future enhancement once a maintainer provisions a secret; not required for the
  floor.
- **Trusted-ref confinement plus the maintainer pre-merge gate only.** No fork-PR coverage at all.
  Retained as the *backstop* for the fidelity the digest guard cannot reach (below), not as the floor.
- **Salted digests everywhere (chosen).** A server-side floor on every push and pull request, forks
  included, with no secret and no list disclosure.

## Consequences (determinism, portability, performance, coverage)

- **Determinism / offline.** The guard is standard-library only: no network, clock, or locale
  dependence. CI runs it with a bare Python and no install step.
- **Portability.** It is a repository-level check, engine-agnostic and absent from every engine's
  dependency tree, so it implies no TypeScript or Java port and does not touch the no-learned-components
  boundary.
- **Performance.** It hashes the n-grams (up to `ngram_max`) of *added* lines and of the in-range commit
  messages only — linear in the size of the change, not the repository.
- **Coverage limit (honest).** A one-way digest can only match token- and phrase-exact normalized
  occurrences. It does **not** catch a term embedded inside a larger token, nor a term written as a
  regular expression in the private list. That fidelity stays with the maintainer's local
  `pre-commit` / `commit-msg` / `pre-push` hooks and with pre-merge review; the digest guard is the
  server-side floor that additionally covers fork pull requests. This division is deliberate, not a gap
  left open.
- **Residual risk.** A committed (public) salt permits an offline dictionary attack against the digests
  for low-entropy terms. The salt still defeats precomputed and cross-repository rainbow tables, the
  committed file carries no cleartext, and exact-phrase fidelity is covered by the local hooks. This is
  the accepted cost of a floor that also protects fork pull requests without a secret.

## Verification (the checks that prove the decision holds)

- `tools/leak_guard.py --self-test`, run as a step of the `leak-guard` job, plants a harmless made-up
  sentinel token and a sentinel phrase, proves the guard catches both with a real location and **without
  echoing the sentinel**, proves clean content and clean messages clear, and re-proves that every data
  line of `tools/leak_tokens.hashes` is a salted digest (`^(both|message) [0-9a-f]{64}$`) — so a cleartext
  regression in the digest file fails the build.
- The `leak-guard` job additionally self-scans its own committed artifacts and scans every push/PR diff.
- The `spec-validators` job runs both validators; each rejects a planted-bad artifact (an incomplete
  vocabulary graph; an emptied example that no longer satisfies its schema), so wiring a no-op validator
  into CI would not pass.
